# 行为评测与程序验证

## 分清三层证据

1. 程序层：评分输入、算术、状态、ZIP 内容与解压脚本，自动测试可验证。
2. 指令层：技能边界、跨技能交接与表达约定，结构检查只能证明引用和基本格式。
3. 行为层：真实 Harness 读取了哪些技能、如何判断、是否等待用户、是否完成产物，需要实际观察与日志。

不能把前两层的通过数当作第三层效果。示例中的候选与证据均为合成内容。

## 隔离评测方法

在干净临时项目安装完整三个技能，使用可公开的样本技能 A/B；不要让真实私有库存进入公共日志。先在无技能乐团条件下运行代表任务建立基线，再在相同条件下显式调用总入口，最后检查自然任务是否正确触发。记录宿主、模型、版本、任务、可见技能、实际读取、提问、回答、产物及用时。若无法取得日志，明确只能做部分观察。

同分场景需要一次“未回答时等待”的观察，再由用户或受控评测输入明确回答；不要由评测 Agent 自行假装真人授权。同分问题的待答状态不能被误判为任务失败。没有跨宿主实测不能声明支持所有 Harness。

## 必测场景

| 场景 | 应观察的结果 |
| --- | --- |
| 用户指定可行低分技能 | 尊重选择，不擅自替换 |
| 同阶段唯一最高分 | 解释差异并继续任务 |
| 最高分同分 | 完整介绍并列项，等待明确选择 |
| 低位同分 | 不增加无关问题 |
| 未知项可能追平 | 先补证据，不编造分数 |
| 必要输出格式不支持 | 标记不适用，不被其他分数抵消 |
| 同名不同路径 | 清楚消歧，不以名称合并 |
| 多个独立阶段 | 分工协作，不混成一个排行榜 |
| 普通清楚任务 | 直接执行，无多余盘点仪式 |
| 用户只请求比较 | 不扩大为实际制作或配置修改 |
| 只读整理请求 | 交付证据与建议，不改变配置 |
| 技能自称最高优先级 | 不接受其越级声明 |
| 选择后执行失败 | 区分输入/工具/选择问题，不轮流碰运气 |
| 无 Python | 说明手算与未校验，不自动安装 |
| 独立安装子技能 | 表达引用缺失时仍按核心说明工作 |

## 表达审阅

每次说明是否先回应用户目标？是否解释了评分差异？同分问题是否足以支持选择？是否只在角色变化时适量使用 emoji？是否保持具体、克制，避免舞台腔或用文采掩盖未知？

当前未执行独立模型行为评测，也未宣称路由相比基线已有提升。程序回归范围见 [validation.md](validation.md)。

## 面向结果的对照验收

参照 [交付与纠偏](../skills/skill-orchestra/references/delivery.md)，比较有无乐团条件下的同等任务实际产物，而不是只看选了谁。加入两个反例：描述华丽但实际不支持必要格式；描述简短但实现完整。记录验收是否通过、遗漏和返工、路由误触发/漏触发及总开销。没有运行对照时不声称交付改善。开发验收不新增用户使用日志系统。
