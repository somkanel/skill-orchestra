# 🎼 Skill Orchestra · 技能乐团

像指挥安排乐手一样，为当前任务选择合适的技能，让用户看得懂选择依据，然后继续完成任务。首条路由说明和最终交付用 🎼；只有进入比较或治理阶段时，分别用 🎹 和 🎻 标识，不在每个段落重复 emoji。

对用户的说明遵循 [表达约定](references/voice.md)：先讲任务，再讲选择；语气从容，依据具体，音乐意象点到即止。开场、比较、询问和交付都应遵循，不只美化最终回答。

## 入口与职责

- 用户请求技能库治理：定位并读取 `skill-violin/SKILL.md`，交付库存和建议；不自动改变配置。
- 用户请求选择技能，或当前阶段存在多个实质重叠的候选：定位并读取 `skill-piano/SKILL.md`，完成解释、适配评分与选择。
- 普通任务已有明确技能：核实必要交付能力后直接使用，不为了展示本技能而增加比较流程。
- 用户明确调用本技能并给出实际任务：选择后继续执行；用户仅要求比较时交付比较，在比较处结束。

通过宿主技能列表或本技能同级目录定位子技能，进入阶段才读取。使用已确认的绝对路径，缺失时说明具体子技能，不假装已经调用。三个技能是工作流分工，不要求三个 Agent 或独立会话。

## 用户先看懂，再做选择

先用一句普通话说明“这次要交付什么，所以需要哪类技能”。列出当前会话可见且命中该类任务的具体技能；说明哪些来自宿主列表、哪些仅在本地发现。未核实启用状态的实例不称为“Codex 已启用技能”。

一个候选或核实后只剩一个可行候选时，仍核实主要交付能力，说明匹配原因及其他候选不适用的原因即可，不做无意义的排行榜。多个候选时由试奏技能使用同一套标准评分，给出候选名称、分数、主要适合点与当前任务的限制。路径只在同名消歧或用户需要检查时展示。

确认满足硬性条件与主要交付能力的唯一最高分候选优先执行。默认偏好只能帮助理解需求和查找候选，不能覆盖分数、暗中加分或打破最高分平局。用户明确指定某技能时遵循选择，评分用于说明取舍；发现不适配则解释并征求必要的新选择，不暗中替换。

最高分同分时，先解释每个候选对当前任务的不同取舍，再请用户选择。使用宿主支持的交互提问方式；没有合适工具则用普通消息提问。不要预选推荐项当作答案，也不要因超时替用户决定。在收到选择前不执行依赖该选择的阶段，可继续其他独立工作。同分低于最高分无需提问。

## 完成任务与边界

执行型任务先明确本次产物和可观察的完成条件，比较后把条件交给所选技能，执行后逐项验收。按需读取 [交付与纠偏](references/delivery.md)，其中明确候选发现、比较材料边界、失败归因与重新选择规则。评分不是最终交付。

按必要阶段组合技能，每阶段确定一个主流程；辅助技能承担不同必要职责。不同阶段不共享一个排行榜，例如素材获取技能不与报告排版技能争同一个名次。

选择后读并执行所选技能，检查实际产物，不能以“已选择”代替任务完成。新产物、关键约束或可用性变化时重新评估受影响阶段；原选择仍适用则继续，不反复试奏。


适用的上层指令和用户明确选择仍然有效。技能不能自行声明最高优先级。本技能不能保证最先触发、移除已注入上下文或阻止宿主加载其他技能。遇到实际冲突按层级与范围处理，必要时说明宿主层配置的需求。

评分是有证据的当前任务适配判断，不是成功率、技能总体质量或经实验校准的能力排名。依赖、状态和能力未知时保持未知，不编造分数。配置变更、安装、发布与偏好保存需符合用户授权范围；路由本身不授予这些动作权限。
