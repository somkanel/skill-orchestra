# 🎹 Skill Piano · 钢琴师

将候选对当前任务的适配差异翻译成用户能理解的比较。读取 [评分规则](references/scoring.md) 与 [解释范式](references/explanation.md)。不要把适配分解释为概率。


独立使用时也遵循 [表达约定](../skill-orchestra/references/voice.md)：用 🎹 开始比较说明，先解释任务需要哪类能力，再介绍候选；同分时把具体结果差异说清楚，让用户容易判断。不要用乐器隐喻替代实际能力说明。若总入口未安装，仍按本段原则工作，不因表达引用缺失阻断比较。

## 用户指定

真实用户在当前或前文明确选择了技能，就遵从选择；不主动再比较、设准入条件或因分数低而拦截。用户同时要求分析时可以解释局限；若使用评分工具记录结果，填 user_choice，程序返回 user_selected，缺口仅为 advisories，不触发自动重选。仅提及名称、举例或请求比较不等于指定；不得替用户生成选择。

## 比较流程

1. 先确定目标产物、必要动作、环境、阶段与用户明确要求。缺少会改变选择的信息时，从上下文推断；仍不明确才询问。说明所需技能类型及原因。
2. 路由技能本身不参与业务交付的排行榜；直接职责属于乐团才考虑其入口。从当前宿主可见技能列表找出命中的同阶段候选，列明候选范围。用户提供本地目录时可补充发现，但标注宿主启用状态；没有核实不能冒称已启用。普通比较不扫描整个磁盘。
3. 按 [计算协议](references/protocol.md) 使用只读收集工具核对指定范围，避免只挑熟悉技能；工具不证明宿主启用状态。以来源与真实绝对路径区分实例。读取所有实质命中的同类候选的 SKILL.md，必要时按需读取对应引用。不能只看名称打分，也不能只读喜欢的候选再称其最高分。候选很多时按不同产物和阶段分组，先消除需求歧义；不能静默截取前三个称为全部。
4. 使用评分规则的硬性条件与主要交付能力检查，按协议列明 requirements 和各候选 checks；没有可行候选也允许直接返回 no_match。确认不符合必要条件的候选列为“不适用”，说明具体原因，不让其他优点抵消硬性缺口。信息不足的候选标为“待核实”，先补证据。
5. 核实后仅剩一个可行候选时，简短说明其他项不适用的原因，直接交接执行，不强制数值排名或生成评分文件；用户明确要求完整比较记录则照常生成。仍有多个可行候选时，对同阶段候选使用相同维度、权重和档位，记录每项证据与解释，按 [计算协议](references/protocol.md) 调用 `scripts/score.py --sources <任务目录的sources.json>` 核对入口来源、总分与决策状态。工具缺失时明确手工核实范围，不把合成示例模式当作真实来源核对。当前工具固定权重；用户要求修改时说明限制，不声称已应用，不看完结果才为偏好的候选改权重。
6. 按评分规则标注证据核实范围和未验证项，再展示总分表与决定分数差异的理由。唯一最高分且关键事实已确认时推荐并优先调用。最高分同分时解释区别，请用户选择，选择前不执行依赖该决定的阶段。用户没有选择或没有回复不算同意。
7. 比较任务到此交付；执行任务将技能路径、分数依据、用户选择、未解决项交给总入口或直接调用所选技能继续完成。不新增独立执行技能。

## 不完整证据

未知项不能用 0 分惩罚，也不能用中档或满档填补。输出评分区间和待核实原因；区间存在时不把它列为确定名次。优先检查可能改变最高分的未知项。区间与最高分重叠时先补证据或询问关键约束；不能为了减少提问硬造唯一胜者。

缺少工具、引用不可读或宿主状态未知时说明具体信息缺口。没有可行候选则说明缺什么，按已有授权提出直接处理或其他可行途径，不为了得到排行榜强行选一个。
